# LAM attendance: ID cards, phone biometrics and IoT fingerprint devices

## ID card attendance

The member ID card generated by the dashboard carries a random QR credential. Open **Scan member ID card** and allow camera access. The camera reads the QR locally, then automatically opens the front camera. The live face capture is compared on the server with the member photo already enrolled in the private member-photo bucket. Attendance is recorded only after a successful match. The QR is not a member URL and does not expose the member's personal details. Use HTTPS for camera access on deployed sites.

## IoT fingerprint terminal

This project now includes a device-authenticated server endpoint and a Supabase migration for fingerprint terminal integration. A compatible terminal (or a vendor gateway/agent connected to it) must perform fingerprint matching on the terminal and send the matched terminal user ID—not fingerprint images or templates—to:

`POST /api/iot/fingerprint`

Headers: `Content-Type: application/json`, `x-device-timestamp: <unix-seconds>`, `x-device-nonce: <unique-random-value>`, and `x-device-signature: <hex-hmac-sha256>`. Sign the exact raw request body with HMAC-SHA256 using `IOT_ATTENDANCE_DEVICE_SECRET`; the signed message is `<timestamp>.<nonce>.<raw-body>`. Requests older than 60 seconds and reused nonces are rejected.

Body: `{"device_user_id":"TERMINAL_ENROLLED_USER_ID"}`

The endpoint validates the signed device request, enforces a short timestamp window, rejects replayed nonces, and calls `record_iot_fingerprint_attendance`. The function looks up the enrolled member, records check-in on the first scan and check-out on the second scan for the UTC attendance date, and prevents concurrent duplicate scans.

### Setup

1. Apply `supabase/migrations/202611180001_iot_fingerprint_attendance.sql` in the Supabase SQL Editor.
2. Set `IOT_ATTENDANCE_DEVICE_SECRET` to a random secret of at least 32 characters in the server environment. Never put it in a `NEXT_PUBLIC_` variable or in terminal firmware visible to end users; store it in the device gateway's secret store.
3. Set the matching `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` server-side. Never expose the service-role key in browser code.
4. Enroll each member's fingerprint in the manufacturer's terminal software. Copy the terminal's opaque enrolled user ID into that member's `iot_device_user_id` field in `attendance_members`.
5. Configure the terminal/gateway to POST the matched user ID to the endpoint. Use the vendor's signed callbacks or a VPN/private network as an additional protection where supported, and rotate the shared secret if a device is lost.

The exact device model matters: ZKTeco, Hikvision and other vendors use different SDKs, callback formats and network protocols. This endpoint is the normalized integration layer; a vendor-specific bridge may still be needed.

## Phone fingerprint / Face ID

A normal website cannot read a phone's fingerprint sensor or fingerprint template. Android and iOS keep biometric data inside the operating system's secure hardware. The supported web approach is WebAuthn/passkeys: the phone asks the owner to authenticate with fingerprint, Face ID or device PIN and returns a cryptographic assertion. To use this for member attendance, the application must add a verified WebAuthn registration/assertion service and bind each credential to a member. Do not treat a browser prompt or a locally stored credential ID as proof of identity. This package does not claim phone-biometric attendance is live until that server-side credential verification is deployed.

## Default administrator

The requested first-run credentials are `superadmin` / `password123`. To initialize the account, set `ATTENDANCE_ENABLE_DEFAULT_ADMIN_BOOTSTRAP=true` temporarily, deploy, open the sign-in page, choose **Set up the first administrator**, and submit those credentials. The bootstrap claim is one-time and creates the `superadmin` role. Then turn the environment switch off and change the password immediately to a unique password. Do not leave the default password enabled on a public deployment.

For normal setup, the existing one-time `ATTENDANCE_ADMIN_SETUP_TOKEN` flow remains available. The service-role key must remain server-only.
